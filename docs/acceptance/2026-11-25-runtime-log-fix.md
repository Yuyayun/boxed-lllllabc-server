# 1.0.5-fix.1 运行日志修补

日期：2026-11-25。前端分支 `codex/1.0.5-legacy-recovery`，后端分支 `codex/1.0.5-log-hardening`。本次为开发分支补修，尚未合并或正式发布；两个 main 仍为已发布的 1.0.5，修复分支推送不代表正式发布。

## 经代码及夹具确认的问题

- 存储线程空闲时退出，没有待处理请求可遍历，原实现漏记退出原因。现在记录一次线程故障、原因代码、退出码及受影响请求数量；主动关闭不报故障，不为队列内每条请求重复报退出。
- 重启后首次核对清空任务，工作线程尚未读到任务登记时，错误可能被猜成迁移。现在先记住通过校验的前端任务类型；没有可靠类型就显示“类型待核对”，不猜归属。
- 连接检查可能抢占每分钟一次的普通成功采样。现在只采样正式备份提交等最终写入；连接检查、读取和暂存批次成功不写普通日志。
- 取消读取、版本变化等正常保护停止混入错误页；任务和请求关联号默认不可见。现在将这些情况显示为提示，保留真正数据库故障的错误分类，并显示简短关联号。
- 日志文件写入失败时，原错误可能已被标记成“记录过”，终端只剩一条泛泛的日志不可写提示。现在保留首次日志不可写提示及本条关键原因的终端兜底，重复情况仍合并。

## 恢复过程记录

恢复沿用现有操作保护记录的编号，同一聊天使用稳定的匿名关联号；不新增恢复数据库字段。记录开始、请求酒馆保存、实际重读核对完成，以及必要的阻止或失败原因。旧数据无法确认的原因区分为缺少整聊依据、校验不符、先后关系不明及正文缺失；不改变恢复判定。

“恢复已确认”必须同时满足原生聊天核对及原有备份保护要求、条件核销返回该恢复根记录的 ID、再次读取确认该记录已消失。保存接口刚返回、聊天文件不一致、保护记录未能核销时均不提前宣称完成。页面重载后仍可用原恢复编号关联，未能保留的来源类型不猜测。

日志只接收受限字段和固定描述，不接收聊天正文、原始聊天键、文件路径、自定义错误文本或完整备份。匿名关联号用于排查，不作为恢复凭据。日志失败不会改变保存或备份结果。

## 数量与容量

- 普通成功每分钟最多一条；连接检查、普通读取、逐楼层和暂存批次成功不加行。
- 同类异常一分钟内合并。后续保留的记录附带合并数量，不为合并数量另开定时日志。
- 普通常规突发限制为每分钟 60 条；必要线程故障、真实恢复关键节点、存储任务重要节点保留，不因其他噪声丢掉最终结果。因此 60 不是所有关键操作合计的硬上限。
- 恢复诊断异步发送，队列最多 32 项，关联和去重缓存各最多 256 项；连接失败冷却一分钟。常规成功恢复仅三个关键节点，与聊天楼层数无关。
- 运行日志仍按原规则分段（默认约 2 MiB），正常已结束组约 7 天、异常或恢复过的组约 30 天；未结束存储任务不按年龄删除。聊天恢复诊断按日分组，不新建永久待处理日志组。
- 每分钟至多一次异步日志目录可写性检查，只打开关闭文件，不追加检测行；实际写入恢复后才解除已知写入失败提示。

浏览器使用真实 IndexedDB 和 HTTP/SQLite，以实际恢复控制器及保存核对控制器验证三个节点同编号，以及原生文件不符时保留保护、不记完成。保留并重跑原有旧数据恢复及新版操作保护回归。原始证据在本地 `.local-test/log-fix-20261125`，不进入安装包；先前审查复现位于 `.local-test/log-audit-20261125`。

前后端均使用后缀 `1.0.5-fix.1`。IndexedDB 9、SQLite schema 4、协议 6 和操作保护记录格式不变，不清库或迁移。后端新增独立 `recoveryLogs: 1` 能力；旧后端不支持时，前端跳过新增诊断请求，旧数据恢复仍可工作。旧前端仍能连接新后端，但不会补发新增恢复过程节点。共享日志模块同步至后端 vendor；未提交前 ORIGIN 保留已发布基准 revision，并标记 `worktreeModified: true`。

所有验证使用隔离合成数据，没有操作用户日常聊天或真实备份库；Termux、Safari 及用户现场原库未作实机验收。
