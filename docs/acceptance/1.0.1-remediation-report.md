## 01：正常迁移减少两轮完整复核

正常流程现在为：分批清点 → 分批搬运并读回 → 一次完整目标验收 → 一次完整来源复核 → 轻量提交及提交结果确认 → 启用和收尾。

| 检查点 | 原先保护的窗口 | 本次处理 |
|---|---|---|
| 清点后立即完整复查来源 | 清点后来源变化 | 正常新任务省去这一轮；发送每批之前本就重新读取来源并与已登记内容核对。中断恢复仍先完整核对来源。 |
| 每批目标读回 | 传输、写入错误及重复请求 | 保留，未减少。 |
| 提交前完整目标验收 | 已验批次后来损坏、遗漏/额外记录、全局关联 | 保留一轮。 |
| 提交前完整来源复核 | 搬运期间来源被外部改动 | 保留一轮，启用前再检查来源修订及任务身份。 |
| 提交后完整目标验收 | 失联期间内容变化、提交响应丢失及实际提交结果不明 | 本次运行收到成功回执时改为核对持久回执、数据区、修订和已完成的验收标记。恢复/响应丢失时仍完整读回；旧配套端若在提交时作废验收，也仍走完整核对。 |

理由：提交事务只改变活动数据区及修订，不改写正文；它在同一事务检查目标验收记录及旧修订，数据区持续受锁保护。不会仅凭前端内存标志猜测提交成功。恢复时不复用上次进程的可信度。

`migration-read-budget.test.js` 对两方向验证：7 条记录、每批 2 条，正常任务只调用一次 `startSourceCheck` 和一次 `startSeal`，各 4 次分页步骤；4 批仍全部 `verifyBatch`。同时计数 SQLite 实际返回的正文记录：来源检查及目标验收各至多 17 次，逐批验货 14 次，提交正文读取 0 次。计数包含每页预读及检查点登记前的再次读取。

保留故障验证：清点后来源变化、最后一批之后来源变化、最后来源检查之后修订变化、已验目标损坏、提交修订变化、提交响应丢失、重启后已验批次损坏、各阶段恢复/撤销/收尾，以及旧配套提交标记回退路径。原位置与被覆盖前的目标按阶段保护。

这不宣称能拦截任意外部程序在任意两条指令间绕过数据锁、同时篡改正文和修订登记。正常写入仍受持久锁限制，来源实际内容检查仍保留。

## 分组 3：实测结果与后续方案（本轮保持策略）

### 02：恢复时重验已确认批次

真实 479 MiB 文件任务，在已核验 **3,405 条 / 191 批**后中断、关闭并重新打开仓储，再重建调度器恢复。重验这 191 批约 **3.526 秒**，完整恢复约 **37.565 秒**，来源与目标最终内容一致。已验批次篡改的既有回归仍拦截。

结论：有可测成本，但它保证在续搬前实际检查中断期间的数据变化，不能直接删除。

后续可行方向：让本次恢复中已经实际读回的批次纳入本次最终验收覆盖范围，避免稍后重复读取同一正文，同时仍检查全局数量、额外记录及关联。需要为覆盖范围、修订与持久锁建立明确绑定，并证明恢复中再次中断、旧回执损坏、内容被改不会静默通过。这比简单删循环复杂；在实机证明这几秒构成瓶颈之前，建议保留当前前置复验。

### 03：每批容量状态请求

在同量级数据库、真实路由和工作线程下，初始化完成后连续执行 **257 次 HTTP 状态查询**，合计约 **608.6 毫秒**，中位 **1.94 毫秒**、P95 **4.69 毫秒**、最大 **21.85 毫秒**。完整宿主两方向流程总状态查询为 263 次，修改前后保持相同；本轮没有改动其频率。

结论：调用量确实多，但这台机器上不是主要耗时，不能据此推断 Termux 相同。

方案：开始时仍对整份迁移作保守空间预检；搬运时按累计写入预算或经过时间刷新余量，替代每批一次，可先评估“约 5 秒或约 32 MiB，以先到者为准”。缓存值必须扣除已消耗预算，查询失败不能猜测空间充足，真实 SQLITE_FULL / QuotaExceededError 的批次回滚和任务保留仍为最后防线。阈值需手机实测后决定。初始不足、途中不足、状态查询失败及真实 SQLite 空间限制回归已覆盖。

### 04：SQLite 常规启动审计

当前结构 479 MiB 数据，直接初始化检查约 **2.3–2.65 秒**；SQL 实际返回 **4,805 次正文记录 / 533,953,486 字节**，包含每页预读。真实 HTTP 首次状态请求含线程启动及准备约 **3.480 秒**。本轮未改变审计策略，不能把不同试跑的波动说成启动优化。

正常重启、损坏载荷、未知表、旧约束/WAL 库升级中断、强制终止工作线程、备份损坏或缺失的回归继续运行。旧升级故障测试使用 231 条夹具；不能冒称本轮重新做过所有旧结构的 479 MiB 性能对照。

方案：常规重启先保留完整审计，因为直接跳过会减少离线损坏检测。优先评估旧库升级完成后的重复审计：若本次升级已经完整验收新数据区，可把该验收与提交修订绑定，随后只核实结构/登记及修订，不再重复扫同一新数据区。必须补升级验收后内容变化、坏元数据、异常表及中断重启测试，并对同量级旧库测前后差异，再决定实施。

### 12：暂停时三次取消验证定时器

执行实际 index.js 暂停回调，配合真实验证控制器和操作闸门，控制两个异步排空窗口：三个取消点全部保留时待执行定时器为 **0**；仅保留前两个或第一个时都会剩下 **1** 个新安排的验证。三次取消合计约 **0.42 毫秒**，不是大数据迁移的主要耗时。

结论：目前存在实际异步保护作用，本轮保留三处。

后续如需简化，给保存验证器提供明确的暂停/恢复状态，在暂停开始后禁止排入新验证，等已有事件与操作全部排空，再统一取消一次；需验证迟到的响应、排空期间新安排、退出暂停后恢复。不能只删看起来重复的函数调用。
