## 数据区方案与兼容性

选择增加空数据区，而非给已有每条记录加代号、重建整库主键。相比提交时复制全部数据，该方案让新数据能直接写进将来正常使用的结构；相比统一分代大表，它避免为了支持代号而在升级 1.0.0 时重写全部正文。

- IndexedDB schema **7→8**：保留原来的七个业务仓库，新增 `__boxed_next_*` 七个空仓库及相应空索引；业务键和记录内容不变。现有迁移元数据仓库保存 `active-dataset`，缺省为 0，非法值拒绝操作。
- SQLite schema **3→4**：保留 `records` 及索引，事务内增加空的 `records_next`、聊天和快照分页索引。新增元数据标记，不对原 `records` 执行 UPDATE、INSERT SELECT 或删除。
- 正常业务接口不变；IndexedDB 在同一个事务中读取活动标记、检查锁并执行业务操作；SQLite 在数据库事务内解析固定表名，缓存按实际 SQL 区分数据区。
- 内部目标启用原语检查持久锁、任务身份、验收阶段、清单和修订号；活动标记、修订号与提交回执在同一库内原子写入。重试必须核实实际活动标记和修订号，回退不得覆盖提交后的新写入。
- 这只保证**目标库内部**提交原子性，不代表前端控制库与目标库具备跨库原子性。后续状态机仍需处理两者之间的中断窗口。
- 内部原语尚未接入路由或存储切换 UI，测试中的已验收回执由夹具明确构造。没有把整份迁移标记为成功，没有把旧迁移流程替换为未经验证的新版流程。
- 旧迁移流程在活动区为 1 时拒绝执行，避免把新活动数据区误当作旧布局操作。旧的未完成任务登记和锁继续保留。
- 当前生产协议仍为 5；新版迁移 API 接入时再升级协议与能力协商，不能仅依据正式版本字符串判断可用性。

## 第二轮：分批清点、逐批验货与持久检查点

状态：内部引擎完成并通过下列测试。**不是完整 1.0.1，也未将旧版 UI 自动切换到新引擎。**

### 实现

- 新增前后端共用的 `batch-transfer.js` 和 `transfer-batch-format.js`，IndexedDB 与 SQLite 各自实现事务驱动。SQL 表名只来自内部的两套固定数据区。
- 来源只在正式数据区上分页读取并加持久锁，不再先把全部正文复制到 transfer_rows。每页限制 100 条/2 MiB；保留原先单条最大 8 MiB 的规则，超过软分页字节预算的合法单条单独处理。支持用更小预算工作。
- 目标准备阶段每次只清理一页非活动区，原正式区保持完整。没有整库 DELETE、换表或 INSERT SELECT。
- 批次绑定任务 ID、批号、连续序号、主键与逐条摘要。目标收到批次后仅登记 written；**实际读回内容、关联检查通过，且确认写回事务内数据仍未变化后**，才原子登记 verified 和进度。
- 只允许一批已写入未核验的数据，避免调用方无限堆积待验批次。重复写入先重读实际内容；缺失或变化直接拒绝，不靠重写掩盖故障。
- 登记簿保存游标、分类型计数、累计摘要、批次确认状态、逐条索引、快照楼层计数及最近有效进展。不保存额外的整份正文副本。新引擎的登记保存在既有迁移元数据仓库/plugin_meta，不需要再次升级 schema。
- 最终验收拆成 `startSeal` 与多次 `sealStep`。逐页核对目标实际记录的索引、摘要、聊天/快照关联和各类型数量，发现缺失、额外记录或不完整快照均不转正；累计清单与来源一致后才产生第一轮轻量提交所需的 verified 回执。
- 目标物理主键排序与来源可能不同（例如 IndexedDB 数值键与 SQLite JSON 文本键）。最终验收用逐条登记索引定位来源摘要，配合全覆盖与计数核对，不错误依赖两端物理排序一致。
- 对单条记录的格式检查、序列化和摘要计算合并复用，避免新引擎在每批中无谓重复序列化大正文；既有摘要格式和业务记录含义不变。

内部阶段：

```text
来源：加锁 → capturing（分页清点、登记、可重发）→ captured
目标：加锁 → preparing（逐页清理非活动区）→ staging
      → 批次 written → 真实读回 → verified（逐批循环）
      → checking（逐页最终验收）→ verified（整项任务）
      → committed（目标库内轻量启用；跨库控制切换尚待下一阶段）
```

- IndexedDB 控制库版本 **1→2**，仅调整小型控制记录的初始化规则，不复制备份正文。保留已有 v1 的活动位置/任务；兼容 v1 尚未写入默认值的纯 IndexedDB 状态。新版控制记录若缺失则报错并阻断，不再因单条记录缺失而默认为另一个位置。控制记录和迁移事务使用 strict durability 请求。

### 恢复依据与取舍

正式调度**先逐页完成来源清点并持久保存完整清单，再开始搬运**，没有把未读部分假定为未变化。这增加了搬运前的清点时间，但清点全程有真实进度、内存有界且不复制整库正文；不把它宣传为已实现“清点尚未完成就开始所有搬运”的交错流水线。

- 清点尚未完成就中断：无法证明未读部分在重启期间没变，安全撤销本任务，保留来源现有数据和目标原正式数据，不凭不完整清单续搬。
- 来源清单完整后中断：分页重新读取真实来源，与最初清单的逐项内容/总摘要、数量和键顺序比较，不能仅相信修订号。然后核对已确认目标批次，才继续未确认批次。
- 最终验收及目标提交前再次分批复核来源；目标提交后分批读回实际活动区并核验，再将前端控制记录和激活阶段一起持久切换。目标提交、前端控制记录之间没有被描述为跨库原子事务。
- 来源修改、插入或删除（即使不更新 revision）会使旧清单失效；转入持久 `aborting`，回退未激活的目标标记，分批清理暂存和登记，再释放锁。源原始数据不参与删除。
- 控制记录已经 `activated` 时只能继续收尾，不再误回滚正式目标；此后来源外部变化仍保留其现有内容，不把它还原为任务初始版本。
- 新任务的旧目标/暂存清理、批次索引/计数清理都限制单次工作量；任务终态回执保留，源数据保留，持久锁在两端收尾后分别释放，最后清除前端任务记录。中断后可识别已经收尾/释放的部分，重复请求不重搬正文。

```text
working：完整来源清点 → 分批搬运/验货 → 最终验收 → 来源复核
  → committing：目标轻量提交 → 提交后分批验收
  → activated：控制记录选择目标（或确认清空）→ 目标确认启用
  → 分批收尾 → 两端释放锁 → 清除 journal

未激活阶段放弃/发现不一致：aborting → 目标回退 → 分批清理暂存/登记
  → 两端释放锁 → 清除 journal（活动位置仍为来源）
```

### 界面与超时的本轮范围

- 启动发现任务先阻断，显示“继续核对并恢复”或“继续完成收尾”，不会自动续搬或选择另一端。未激活任务可进入带勾选确认的“放弃本次迁移”；撤销中断显示继续完成撤销，已激活任务不提供放弃。
- 新任务可以在当前有界步骤结束后暂停；清点阶段尚无完整基线时明确说明恢复可能撤销。进度分别说明清点/核对量，搬运数字只使用目标已核验数。
- 恢复完成后刷新实际存储状态；若启动曾因恢复而中断，重新进入原正常备份流程刷新状态，避免界面长期残留“存储操作待恢复”。
- 前端新请求中断/AbortError（包括数字 code 20）归为结果未知，持久任务/锁保留。后端新分批请求等待超时仅取消该请求、保留排队项直到工作线程确认，不再因此终止整个 SQLite 工作线程；已有队列上限不放宽。
- **本轮没有宣称固定 15 秒的所有问题已经解决**。按实际进展的监工/心跳、自适应等待、启动 quick_check、原状态统计/容量探测、旧版恢复及旧库升级中的长工作仍待下一轮处理。

### 启动检查与旧库升级

- 移除启动必跑的原生整库 `PRAGMA quick_check`，改为真实记录的分页逻辑检查：每页最多 100 条/约 2 MiB（既有较大单条独占页），检查无损编码、主键、记录类型和聊天/快照归属，持有一致读视图并在页间让出工作线程，主线程可接收真实处理量。损坏载荷不会被当作空库；启动错误回执不包含解析载荷片段，日志保留错误代码及所在阶段。**此逻辑检查不是 SQLite 物理 quick_check 的等价实现，不证明空闲页等所有内部结构无损。** 测试中仍显式运行原生 quick_check 验证升级结果，但生产启动不依赖这个长调用。
- schema 3→4 仍只增加空数据区。更早旧库不再使用 `VACUUM INTO` 或整表 `INSERT SELECT` 转换；先在写保护下逐页生成独立 SQLite 逻辑备份，保留原表结构、索引、元数据、旧迁移行及原始编码，包含已提交 WAL 内容，逐页读回核对后才命名为 `.before-v3-*.bak`。备份是逻辑一致副本，不是原文件物理字节镜像；索引在空表上预建，原触发器在备份载荷复制完成后恢复，避免复制时触发业务副作用。
- 备份完成后，原库创建空的新结构及索引，持久登记升级阶段、游标和校验清单；数据库触发器阻止原始表和相关元数据被改写。新结构每页复制/读回/检查点一起提交，避免把大库转换放在一个巨型写事务里，也避免最后整体构建索引。重启先分页复核备份与来源，再从检查点继续。最终完整验收新结构后，才在轻量事务中启用；原表及独立备份都保留到此后，旧表按页删除，最后仅 DROP 已空表。
- 已启用但尚未清理的升级会先复核独立备份和当前新结构，再继续清理。备份丢失、篡改或登记不完整时不清理原表，也不开放正常操作。普通请求须等待初始化完成。备份生成尚未登记就中断时保留 `.bak.pending`；原库未转换，下次重新生成，不擅自删除诊断副本。

### 1.0.0 遗留迁移恢复

- 前后端共用新的 `legacy-recovery.js`，仍沿用旧 `/transfer` 的 status/rollback/finish 语义；正式 HTTP 入口继续禁止用旧 source/prepare/commit 发起长迁移。原创建/提交代码保留用于历史兼容夹具，正式迁移走新版分批引擎。
- 未激活的已提交旧目标：分页清点权威回滚副本 → 持久清理游标 → 分批写回且逐条读回 → 完整复核 → 分批清理旧迁移行 → 持久终态并释放锁。恢复副本在全部核验前不删除。每页修改与检查点同事务提交，重试不会重复写；重载/重启可继续。目标暂时处于恢复中的正式区域仍受持久锁阻断，来源数据从不参与清空。尚未提交目标或来源只按页清理其旧影子副本。
