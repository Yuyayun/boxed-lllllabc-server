## 数据区方案与兼容性

选择增加空数据区，而非给已有每条记录加代号、重建整库主键。相比提交时复制全部数据，该方案让新数据能直接写进将来正常使用的结构；相比统一分代大表，它避免为了支持代号而在升级 1.0.0 时重写全部正文。

- IndexedDB schema **7→8**：保留原来的七个业务仓库，新增 `__boxed_next_*` 七个空仓库及相应空索引；业务键和记录内容不变。现有迁移元数据仓库保存 `active-dataset`，缺省为 0，非法值拒绝操作。
- SQLite schema **3→4**：保留 `records` 及索引，事务内增加空的 `records_next`、聊天和快照分页索引。新增元数据标记，不对原 `records` 执行 UPDATE、INSERT SELECT 或删除。
- 正常业务接口不变；IndexedDB 在同一个事务中读取活动标记、检查锁并执行业务操作；SQLite 在数据库事务内解析固定表名，缓存按实际 SQL 区分数据区。
- 内部目标启用原语检查持久锁、任务身份、验收阶段、清单和修订号；活动标记、修订号与提交回执在同一库内原子写入。重试必须核实实际活动标记和修订号，回退不得覆盖提交后的新写入。
- 这只保证**目标库内部**提交原子性，不代表前端控制库与目标库具备跨库原子性。后续状态机仍需处理两者之间的中断窗口。
- 内部原语尚未接入路由或存储切换 UI，测试中的已验收回执由夹具明确构造。没有把整份迁移标记为成功，没有把旧迁移流程替换为未经验证的新版流程。
- 旧迁移流程在活动区为 1 时拒绝执行，避免把新活动数据区误当作旧布局操作。旧的未完成任务登记和锁继续保留。
- 当前生产协议仍为 5；新版迁移 API 接入时再升级协议与能力协商，不能仅依据正式版本字符串判断可用性。

## 第二轮：分批清点、逐批验货与持久检查点

状态：内部引擎完成并通过下列测试。**不是完整 1.0.1，也未将旧版 UI 自动切换到新引擎。**

### 实现

- 新增前后端共用的 `batch-transfer.js` 和 `transfer-batch-format.js`，IndexedDB 与 SQLite 各自实现事务驱动。SQL 表名只来自内部的两套固定数据区。
- 来源只在正式数据区上分页读取并加持久锁，不再先把全部正文复制到 transfer_rows。每页限制 100 条/2 MiB；保留原先单条最大 8 MiB 的规则，超过软分页字节预算的合法单条单独处理。支持用更小预算工作。
- 目标准备阶段每次只清理一页非活动区，原正式区保持完整。没有整库 DELETE、换表或 INSERT SELECT。
- 批次绑定任务 ID、批号、连续序号、主键与逐条摘要。目标收到批次后仅登记 written；**实际读回内容、关联检查通过，且确认写回事务内数据仍未变化后**，才原子登记 verified 和进度。
- 只允许一批已写入未核验的数据，避免调用方无限堆积待验批次。重复写入先重读实际内容；缺失或变化直接拒绝，不靠重写掩盖故障。
- 登记簿保存游标、分类型计数、累计摘要、批次确认状态、逐条索引、快照楼层计数及最近有效进展。不保存额外的整份正文副本。新引擎的登记保存在既有迁移元数据仓库/plugin_meta，不需要再次升级 schema。
- 最终验收拆成 `startSeal` 与多次 `sealStep`。逐页核对目标实际记录的索引、摘要、聊天/快照关联和各类型数量，发现缺失、额外记录或不完整快照均不转正；累计清单与来源一致后才产生第一轮轻量提交所需的 verified 回执。
- 目标物理主键排序与来源可能不同（例如 IndexedDB 数值键与 SQLite JSON 文本键）。最终验收用逐条登记索引定位来源摘要，配合全覆盖与计数核对，不错误依赖两端物理排序一致。
- 对单条记录的格式检查、序列化和摘要计算合并复用，避免新引擎在每批中无谓重复序列化大正文；既有摘要格式和业务记录含义不变。

内部阶段：

```text
来源：加锁 → capturing（分页清点、登记、可重发）→ captured
目标：加锁 → preparing（逐页清理非活动区）→ staging
      → 批次 written → 真实读回 → verified（逐批循环）
      → checking（逐页最终验收）→ verified（整项任务）
      → committed（目标库内轻量启用；跨库控制切换尚待下一阶段）
```

- 前端自动化：**294/294**，0 失败、0 跳过。
- 后端自动化：Node **24.15.0、22.14.0 各 51/51**，包括原有测试。
- 八个新增真实 SQLite 场景覆盖：分批准备/清点/验货/最终验收、关闭重开、重复请求、乱序、跨任务批次、重复主键、缺失/篡改、来源修订变化、快照/未保存变更与关联异常、回执写入故障、额外目标记录、损坏登记及未知表。安装正文拒绝写入触发器后轻量提交仍能完成。
- 真实浏览器 IndexedDB ↔ 真实 SQLite 双向内部集成：每向 13 条记录，覆盖全部七类仓库；使用 2 条/700 字节的小预算，每向经过 12 个搬运批次与 12 个最终验收步骤。内容、Date/undefined、swipe、快照预览与旧目标保留均一致，页面错误为 0。
- IndexedDB → SQLite 方向实际丢弃写入成功后的 HTTP 响应，重新打开 SQLite 后重试同一来源批次，未重复写入或累计进度。
- SQLite → IndexedDB 方向在写入后重新创建引擎，直接篡改暂存内容会拒绝确认；恢复夹具内容后注入检查点写入故障，验证计数与批次回执同事务回滚，重试后正常推进。
