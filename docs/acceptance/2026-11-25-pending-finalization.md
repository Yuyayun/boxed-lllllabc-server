# 1.0.5-fix.1 保存收尾与持续黄灯补修

日期：2026-11-25。用户授权一次性延后修复。前端 `codex/1.0.5-legacy-recovery`、后端 `codex/1.0.5-log-hardening`，均为开发分支补修；尚未合并或正式发布，main 保持正式 1.0.5，版本后缀仍为 `1.0.5-fix.1`。修复分支推送不代表正式发布。

## 原因与两步处理

已用原生 SillyTavern 1.15.0/1.19.0 复现：`saveReply` 会给上一条用户消息补空 `extra.reasoning`，并在 MESSAGE_RECEIVED 后继续补 AI 的候选信息。1.0.5 对明确楼层的事件复用其他同引用消息的旧快照，GENERATION_ENDED 也只检查末层，整聊操作链因此一直匹配不到正确保存的 JSONL。正常三轮可积累 6、12、18 行 pending。原审查证据在本地 `.local-test/yellow-state-audit-20261125`。

本次保留事件回调中的即时不可变操作捕获，不把删除/编辑/新增延后到 debounce。结束及停止生成时扫描全部消息；异步事件处理后、批量备份前，以及真正读取酒馆保存文件前，另外通过 `observer.settle()` 观察完整差异。收尾变化追加成既有格式的新操作，原操作和消息副本不覆盖。

收尾观察检查聊天键、文件 integrity 和聊天数组身份。加载旧文件或切换聊天会重建观察基线，不能把“重开了旧聊天”当成用户主动撤销删除或编辑。未经过事件捕获的手动/加载入口保留原重置行为。

核对器通过可取消的 effect 队列准备收尾，再固定本轮最终原生哈希。带操作记录的核对等待酒馆生成结束，即使中途页面和文件暂时相同也不提前核销；结束后要求实际文件与终态一致。读取、备份修复、条件核销及发布成功之前继续检查生成状态、聊天身份和终态。期间出现新的变化，不发布绿灯，也不把它误写为“酒馆已保存，备份待补全”。无 pending 的普通绿灯分支保持原规则。

## 已经积累的旧 pending

仅补一次新观察不能接续页面重载前留下的旧链。本次另有一个受限的旧数据确认入口：只识别用户消息中原生自动补的空 `extra.reasoning` 与缺失该属性之间的区别。

它不改文件、页面、原记录或备份正文，也不删除非空思考内容。以现有消息副本的 SHA-256 和原生新增 AI 的位置建立候选历史视图，仅从用户消息的副本视图移除这个空默认属性；随后必须完整匹配原操作的整聊 SHA-256、每个消息哈希、反推前态及连接关系。正文、候选、其他 extra、非空 reasoning 或分支不符均不因此放行。

完整终态优先沿原精确校验路径处理；仅仍有无法确认的操作时才尝试旧默认值入口。已经核销用户记录、只剩 AI 记录及部分核销后缺消息副本的情况，继续利用保存的消息哈希及整聊证明核对。多个无法辨别的候选不枚举自由组合；最多核对 64 个流终点，无法确认的记录继续保留。

较长文件中的前缀只用于没有收缩/恢复的操作集合；删除后的短状态不能被较长旧文件前缀冒充。恢复或快照终点不通过默认值兼容入口，保留快照原有元数据证明。

核对成功后生成的证明仍指向**实际文件及实际备份**的哈希；历史副本位置也使用实际原生消息哈希。原记录指纹、备份写入证明、依赖处理顺序和存储事务中的条件删除仍全部生效。不是“页面等于文件就清空全部 pending”。真实未保存编辑 B 在重开旧文件 A 后继续保留。

## 范围

- 没有增加数据库版本、协议版本或 pending 格式；IndexedDB 9、SQLite schema 4、protocol 6 均不变。
- 后端仅同步共享 `pending-journal.js` 及新 `pending-native-defaults.js`，更新 vendor 清单；存储 API 与条件核销保护不变。旧 1.0.5 后端仍可接收相同格式的证明；此前新增恢复诊断能力仍需配套 fix.1 后端。
- 没有增加运行日志事件或逐楼层日志，沿用已有日志限频。
- 先前明确暂缓的一般红灯分类、无 pending 时绿灯判定、打开面板清除完整备份暂停提醒、空聊天/未打开聊天指示灯，均未顺带修改。
- 先前旧恢复、运行日志、待确认提示文字补修和用户文件保留。
