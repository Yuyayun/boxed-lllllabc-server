# 1.0.5 未保存变更恢复：实现与验收

实现日期：2026-11-24，最终补测与正式交付：2026-11-25。前端分支 `codex/1.0.5-empty-chat`，配套后端分支 `codex/1.0.5-pending`。两端合并至 `main`，配套附注 Tag `v1.0.5` 与正式 GitHub Release，见[发布核对](release-1.0.5.md)。

## 用户看到的变化

删除后，剩下的消息按实际顺序接续。例如 `12345` 删除 `23`，恢复结果就是 `145`，然后继续追加新消息。删除、随后编辑、继续聊天分别记录，不再从稍后的一份聊天里反推整批操作。

仍使用唯一的“恢复未保存变更”入口。旧记录能与现有消息副本组成唯一结果时，直接预览；缺正文、存在无法区分的结果或校验不符时，说明原因并保留原数据。

恢复前追加一份本次恢复的保护记录，原记录留到实际保存并核对成功。页面显示正确、保存接口返回成功，都不单独作为核销依据。切换聊天、修改来源、保存超时或中断时保留保护。

当前聊天为空与没有打开聊天分开显示。空聊天本身没有正文备份可恢复；删除全部楼层仍是一项需要确认落盘的操作。

## 根据源码作出的实现选择

- 使用前端观察和操作日志。删除事件参数不作为楼层号；事件发生时比较前后状态，先绑定聊天身份与消息内容，再异步计算校验和分批写入。每个聊天有独立操作 ID、观察序列和引用，重命名只迁移所属身份。
- 普通连续删除记录删除范围和前后校验，不自动复制完整聊天。插入、编辑和候选变化保留必要消息副本。非连续变化可记录为替换一个范围，保证结果正确。
- 复用已有最近、完整、历史及未保存消息副本。旧结构记录缺少操作细节，不能当作可靠删除指令；只在可用消息组合唯一且符合旧长度、校验和时恢复，候选组合限制为 64，歧义时停止。
- 新记录核对完整原生 JSON，包括扩展字段。反向证明连续操作的先后状态，防止重复删除；条件核销再次核对记录指纹和所需备份。分批中断后，保留操作根记录并接续剩余部分。旧 numeric 消息被后续删除移位时，按证明后的新位置补齐历史副本。
- 显式恢复保存使用酒馆原生保存端点，固定聊天文件、消息和元数据，保留 `force:false` 与原 integrity。避免原生全局保存等待期间切换聊天造成保存目标变化；普通聊天自动保存流程不变。
- 原生重绘会把不存在的 `extra` 初始化为空对象；恢复重绘后仅撤销这项空初始化，保留原保护 JSON。新增了真实内容的字段仍会阻止误保存。
- 本轮没有实施可选的酒馆源码增强或菜单开关。纯前端删除捕获、恢复和核对已独立验证，后端只增加匹配的存储保护能力。

## 数据兼容

浏览器数据库版本从 8 升至 9，仅用于阻止旧前端继续执行会改坏新操作 ID、引用或核销逻辑的写入；没有新增对象仓库、没有改写或清空旧记录。同一浏览器升级后不支持直接降回旧前端。

SQLite schema 仍为 4，存储协议仍为 6，增加 `pendingJournal:1` 能力。新前端遇到缺少能力的旧后端会保留记录并提示更新。新后端拒绝旧客户端整批覆盖日志；旧写法更新完整或最近备份时，不得继续沿用过期的原生校验证明。原有单条 8 MiB、请求 16 MiB、分页读取 32 MiB 等容量保护未提高。

## 文案与错开更新补测

把“未保存改动已保护”改成中性的“改动记录”，列表使用“待确认改动”。说明记录可能是在等待酒馆保存核对，也可能是在等待备份补全；仍有记录不代表酒馆一定没保存。恢复入口继续使用“恢复未保存变更”，没有增加版本选择或第二种恢复模式。

后端 1.0.5 的 SQLite 仍为 schema 4、协议 6，不会主动升级浏览器的 IndexedDB。用正式 1.0.4 前端代码连接当前 1.0.5 后端，验证启动、编辑、完整与历史备份、条件核销均正常；浏览器本地库仍为 8。浏览器本地库升至 9 只发生在新版前端打开它时。

补测复现了真正可能长时间等待的情况：旧页签阻塞一个数据库升级请求，后面的打开请求排队，收不到自己的 `onblocked`。现增加默认 5 秒的打开超时，拒绝迟到连接并取消迟到升级；已有连接收到 `versionchange` 时主动关闭。VersionError 明确提示更新前端和刷新，不降级数据库、不删除数据、不改变活动存储位置。

旧前端试图整批覆盖新版操作记录时，服务器明确返回“更新前端”的原因，不再误报“服务器插件需要更新”。版本不匹配及页签占用的提示不提供“管理清理”按钮。

`tests/browser/run-update-compat-contract.mjs` 覆盖 6 项真实浏览器与 HTTP/SQLite 合同；`BOXED_NATIVE_UPDATE_COMPAT=1` 配合 `tests/browser/run-native-pending-contract.mjs` 验证实际酒馆网页中的旧前端/新后端、浏览器 8→9，以及缓存旧前端时的页面操作和更新入口。此测试只打开更新确认框，不执行 Git 拉取或真实扩展更新。

已经加载在旧页签中的脚本仍需更新并刷新；后端更新不能替换另一个网页内存里的前端脚本。浏览器库已经升至 9 时，旧版前端仍不得读写它；服务器 SQLite 连接不受这个浏览器版本号影响。

## SQLite 不可用时的全页遮罩补修

用户截图中的“存储操作待恢复／SQLite 工作线程不可用”对应旧版存储恢复错误界面，与前述数据库打开排队是不同路径。用户明确补充：当时数据已经搬完，随后新后端配旧前端出现此界面。因此不能根据界面标题认定数据没有搬完，也不能把下面的未完成迁移夹具当作这次历史故障的根因复现。原有 `createStorageSwitchUi.failure()` 会在检测到待处理控制记录或无法读取控制状态时打开模态框并禁止关闭，确实可能把酒馆操作和前端更新入口一并挡住。上一轮错开更新测试未覆盖这条故障路径。

现在只有实际执行中的任务继续使用操作遮罩；收到失败或暂停结果后，增加“暂时关闭（备份仍暂停）”，也支持 Escape。关闭仅移除模态提示，不解除操作门禁和数据库持久锁，不删除任务登记，不选择其他存储位置，不放弃迁移。设置中持续显示备份暂停提示；聊天状态入口和“继续处理存储操作”按钮可重新打开恢复。暂停期间新增聊天不承诺获得箱装备份保护。

`tests/browser/run-recovery-contract.mjs` 在实际 IndexedDB 与 HTTP/SQLite 中断任务上注入工作线程不可用，覆盖 1024px、390px 两种宽度：关闭后输入与更新入口可操作，任务、写入门禁、源数据与目标原数据保持不变；重试仍失败时可再次退出，刷新后登记仍保留，故障解除后能正常接续。原有迁移、清空、暂停、撤销、日志等界面合同继续通过，页面错误为 0。

真实酒馆补测使用 `BOXED_NATIVE_WORKER_LOCKOUT=1`：独立随机 dataRoot/SQLite 目录和端口 18007，先生成真实未完成迁移，再在 HTTP 边界返回“SQLite 工作线程不可用”。验证关闭提示后原生聊天输入、前端更新确认框可用，备份写入仍暂停；从原生聊天状态提示重新进入恢复，核对后目标三条正文与原内容一致。只打开更新确认框，没有执行真实 Git 更新。原始证据在 `.local-test/review-1.0.5-20261124/native-worker-lockout`。

这项补修验证故障界面的退出和任务安全性；截图本身不能解释后台线程为何不可用，不能据此断言由版本更新造成，也不表示 SQLite 故障本身已经被消除。

## 已搬完后再升级的补测

按用户补充的 1.0.0／1.0.1 版本范围，新增 `tests/browser/run-completed-upgrade-contract.mjs`。使用 Git 正式标签中的实际前后端存储模块、真实浏览器 IndexedDB 和 HTTP/SQLite：先完整结束迁移，核对目标收尾凭据为 finished、前端 journal 为空，再只替换后端，保留同一个 SQLite 文件和旧前端。

覆盖 1.0.0→1.0.1、1.0.0→当前 1.0.5、1.0.1→当前 1.0.5 三种后端更新顺序。旧前端保持加载和重新加载后都没有重建迁移，没有迁移请求或迁移遮罩；随后连接不可用、新前端接手，也不把正常已完成任务重开。1.0.0 的通信协议为 5，1.0.1 起为 6；跨此边界的旧前端明确报告协议不兼容，需要更新前端。1.0.1 与当前后端协议一致，可继续连接。旧协议不兼容本身没有在这些夹具中复现截图中的工作线程错误。

另在已经完整结束的任务上，只恢复其激活阶段的前端登记，模拟收尾确认遗留；并先修改目标正文，代表搬完后已有新内容。当前前端只查询完成凭据并执行幂等收尾，不重新复制、准备或提交数据；遗留登记清除，搬完后的新内容保留。这是额外的合成边界验证，不表示已经确定用户当时存在此遗留登记。

三种顺序均通过，页面错误为 0，原始报告为 `.local-test/review-1.0.5-20261124/completed-upgrade-report.json`。本补测覆盖历史存储模块和恢复界面，不是历史完整酒馆网页的端到端回放；此前原生网页错开更新测试使用的是 1.0.4 前端。历史故障的具体线程退出原因仍缺少对应日志，不能承诺已经定位。新版提示已改为“核对上次存储操作”，避免把仍待核对说成数据必然未搬完。
